# Roadmap

An open-source, seed-derived geocoding system: three BIP-39 words plus a number
address every ~2.4 m square on Earth, under a mapping that is private to each
user's seed phrase.

**Tracking rules.** All future work lives in this file. Completed work moves to
`roadmap-progress.md`. No other documents track work — no issue-tracker-of-record,
no separate design docs, no TODO comments used as a backlog. If a decision is
worth keeping, it belongs in this file's *Locked decisions* section or in the
progress log's rationale field.

## Locked decisions

These are settled. Reopening one requires a note in `roadmap-progress.md`
explaining what changed.

### Address format

| Property | Value |
|---|---|
| Wordlist | BIP-39 English, 2048 words |
| Address shape | `word.word.word.NNNN` (three words + 4-digit number) |
| Total address space | 2048³ × 10⁴ = 2³⁷ × 625 ≈ 8.59 × 10¹³ |
| Target resolution | ~3 m square |
| Grid cells (actual) | 55,692,067,744,000 (0.648 of address space) |
| Invalid address share | 35.2% |

*Corrected 2026-08-15: an earlier draft said 2.4 m. That figure was the side
length consuming the address space exactly, leaving no room for grid
inefficiency — 2.4 m needs 103% of the space and does not fit. 3 m fits at 65%
and is what yields the 35% invalid share.*

The BIP-39 wordlist is deliberate: prefix-unique, curated against confusable
pairs, and already supported by tooling in many languages. The trailing number
is what makes a 2048-word list sufficient — without it the list would need to be
~40,000 words.

Roughly a third of syntactically valid addresses decode to nothing. This is free
typo detection and is a feature, not waste.

### Grid

- **Integer only.** Latitude and longitude are `int64` in units of 10⁻⁹ degrees.
  No floating point anywhere in the grid path. This is primarily for
  cross-platform determinism — IEEE-754 rounding differences at cell boundaries
  would make a JS client disagree with the server about which square a point is
  in — and secondarily because integer arithmetic is far easier to prove over.
- **Banded.** 6,553,600 rows grouped into 4096 bands; each band has its own
  column count taken from the cos of its equator-ward edge, so no cell is ever
  wider than 3 m. Cell distortion 1.043; table 48 KB, small enough to ship in
  a WASM payload. Generated by `design/grid_design.py`.
- **Inverting a floor-bucket takes a ceiling.** Cell `c` covers
  `[ceil(c·span/k), ceil((c+1)·span/k))`. Using floor on both sides puts the
  upper edge one nanodegree short and points in that sliver fall outside their
  own cell. This bug was in the first reference implementation and is the
  reason `theorem_containment` is stated separately.
- **Widest intermediate is 4.80×10¹⁸** (lon_span × max columns): fits signed
  int64 with 1.92× headroom, uint64 with 3.84×. Unsigned preferred for margin,
  not required. Proof obligation, not a footnote.

### Mapping

- **Scattered, not hierarchical.** Adjacent squares get unrelated addresses.
  Chosen because a leaked address under a hierarchical scheme would expose the
  whole enclosing coarse block (10,000 squares); under scattered it exposes one
  square. A ten-thousand-fold difference in how fast an attacker reconstructs a
  private map. Secondary benefit: a typo lands somewhere obviously wrong rather
  than plausibly-but-silently 200 m away.
- **Coarse precision is an explicit mode**, not truncation. Two words for a
  block, three for a room — separate encodings, deliberately requested.
- **FE1 generalised Feistel (Black–Rogaway) over Z_a × Z_b**, with
  a = 2¹⁸ × 25 = 6,553,600 and b = 2¹⁹ × 25 = 13,107,200. Product is exactly
  the address space, so the bijection is exact and there is no cycle-walking
  and no probabilistic termination argument. *Corrected 2026-08-15: the
  earlier pair (2¹⁹, 2¹⁸×625) was a 250:1 split, badly unbalanced for a
  Feistel. This pair is 2:1.*
- **8–10 rounds**, HMAC-SHA256 as the round function. Four rounds is
  distinguishable; do not economise here regardless of what has been proved.
- **Key derivation:** mnemonic → BIP-39 seed (PBKDF2-HMAC-SHA512, standard) →
  HKDF-SHA256 → 32-byte Feistel key. Derived once per session and cached;
  PBKDF2 is deliberately slow and must not sit in the hot path.
- **Tweak = grid version string** (`tessarium-grid-1`), and the HKDF salt
  and info strings are `tessarium/v1/salt` and `tessarium/v1/feistel-key`.
  Renamed from `w3wx/*` on 2026-08-15; since no address had been issued, this
  was free. After launch it would invalidate every address anyone had written
  down. Regenerating the band table
  changes every address rather than silently reinterpreting old ones.

### Cryptography and quantum resistance

The construction is entirely hash-based, so it is already post-quantum. Grover
halves effective strength; nothing here relies on factoring or discrete log.

- **24-word mnemonics only.** 256 bits → 128 bits post-Grover. Do not offer
  12-word (128 → 64 bits, too weak).
- **Warn hard against reusing a wallet seed.** Anyone who learns a few
  (address, true location) pairs is doing cryptanalysis against a key that also
  holds funds. Generate fresh.
- Kuwakado–Morii quantum attacks on Feistel require superposition queries to the
  encoder and do not apply to software the attacker does not control. Expect to
  see it cited; it is not a threat to this design.
- ML-KEM and SLH-DSA are only relevant if seed-sharing or location attestation
  ships later. Not needed for the core.

### Implementation stack

| Layer | Technology | Verified? |
|---|---|---|
| Core (grid, Feistel, codec) | F\* | Yes |
| Server extraction target | OCaml (via F\* extraction) | No — generated artifact |
| Client extraction target | C / WASM (via Low\*, later) | No — generated artifact |
| HTTP server | OCaml — Eio or Dream | No |

**Extracted code is never hand-edited.** It is a build artifact, like an object
file. Any change belongs upstream in the F\* source, or it will be silently
overwritten at the next extraction.

**No platform reimplements the algorithm by hand.** One proved source, several
extraction targets. `reference/` and `js/` currently violate this; both are
labelled scaffolding and are scheduled for removal or explicit justification.
`design/grid_design.py` is exempt — it runs offline, emits a data table rather
than shipping code, and its floating-point trigonometry is precisely why it
lives outside the integer-only runtime.

**Trusted computing base:** the F\* extraction pipeline and `ocamlopt` are
trusted, not proved. Say so in the README.

**OxCaml is out of scope** for now. Its unboxed types would address real `int64`
boxing in extracted code, but the gain is invisible behind HTTP, the extensions
are experimental and not backwards-compatible, and hand-annotating extracted
code violates the rule above. Revisit only if a profiler points at the core.

### What proof does and does not cover

Two theorems earn their place:

1. `decode(encode(cell, key)) = cell` for all cells and keys. Follows
   structurally from Feistel invertibility; does not depend on the round
   function being cryptographic.
2. The grid map is injective, **including across latitude-band seams**. This is
   the one that matters. Band boundaries are where two bands can claim the same
   point or leave a gap, and tests miss it because the failure set is
   measure-zero.

Proof does not establish that the grid is *well designed*, only that it is
consistent. It cannot establish that the mapping is unguessable — the strongest
honest claim is "provably reversible for any round function, and unpredictable
assuming HMAC-SHA256 behaves as a PRF." Do not let the README overstate this.

## Phase 0 — Foundations

- [ ] Repository, licence (Apache-2.0 or MPL-2.0), README stating scope and
      non-goals
- [ ] F\* toolchain pinned and reproducible; CI that runs verification on every
      push
- [ ] Clean-room paper trail from day one. Do not read, reference, or vendor
      what3words' wordlist or grid. They have historically been aggressive with
      legal threats against reimplementations; the defence is documented
      independence.
- [ ] Prior-art note in README: Open Location Code (Plus Codes, Apache-2.0)
      solves the public case well. The differentiator here is the per-seed
      private mapping.

Design and reference done; the F\* work remains.

- [ ] Implement `point_to_cell` / `cell_to_point` in F\* against
      `fstar/Tessarium.Grid.fsti`
- [ ] Prove `lemma_edge_inverse` — the floor/ceiling property the reference
      got wrong first time
- [ ] Prove `theorem_containment`, `theorem_injective`, `theorem_roundtrip`
- [ ] Discharge the band-table well-formedness lemmas against the generated
      table (contiguity, totals, `lemma_fits`, `lemma_cells_wide`)
- [ ] Prove `theorem_no_overflow`
- [ ] Emit the band table as an F\*-consumable constant from
      `design/grid_design.py`

## Phase 2 — Feistel and key derivation

Reference done and vectors committed; the F\* work remains.

- [ ] Implement FE1 in F\* against `fstar/Tessarium.Feistel.fsti`
- [ ] Prove `theorem_roundtrip` — note it holds for ANY round function, so it
      does not depend on HMAC being cryptographic
- [ ] Prove `theorem_injective` / `theorem_surjective`
- [ ] Decide whether to take HMAC-SHA256 from HACL\* (verified) or assume it
      at the interface. HACL\* is the better answer if Low\* lands in Phase 6
      anyway.

## Phase 3 — Codec

- [ ] Mixed-radix decomposition (2048, 2048, 2048, 10000) ↔ integer index
- [ ] Address parsing: case folding, separator tolerance, BIP-39 four-letter
      prefix matching
- [ ] Reject out-of-range decodes cleanly (the ~34% invalid space)
- [ ] Prove round-trip end to end: `decode(encode(point)) = point`'s cell

## Phase 4 — Extraction and measurement

- [ ] Extract to OCaml; confirm CI rejects any manual edit to extracted files
- [ ] **Benchmark the encode/decode path on day one.** Expected 3–6 µs per
      encode. This exists so future performance discussions are empirical.
- [ ] Differential test: extracted core vs. the Python reference and the JS
      implementation, millions of random points. Harness pattern already
      proven — see `js/test_vectors.mjs` and the Python/JS fuzz.
- [ ] **Re-anchor the test vectors to F\*.** `vectors/vectors.json` is
      currently generated by `reference/gen_vectors.py`, which makes the Python
      the de facto source of truth for every implementation that checks against
      it. Regenerate from the F\* spec; contents must come out byte-identical,
      and if they do not, something is wrong — which is the reason to do it in
      this order.
- [ ] **Delete `reference/`.** Scaffolding, written because no F\* toolchain
      was available during design validation. Two hand-written copies of the
      algorithm currently exist, which is exactly what the one-proved-source
      architecture is meant to prevent. Removal criteria and interim rules in
      `reference/README.md`.

## Phase 5 — Server

- [ ] OCaml HTTP service (Eio or Dream): encode, decode, health
- [ ] Session key cache so PBKDF2 runs once, not per request
- [ ] Decide whether the server ever sees a seed phrase. Strongly prefer not —
      client-side derivation with the server as a dumb tile helper is the better
      privacy story and should be evaluated before the API is fixed.
- [ ] Rate limiting, structured logging that never logs seeds or addresses

## Phase 6 — Clients

- [ ] Retarget the core to the Low\* subset; extract C via KaRaMeL
- [ ] WASM build from the same source
- [ ] JS client consuming the WASM artifact
- [ ] Verify all targets reproduce the Phase 2 test vectors bit-for-bit
- [ ] Mobile: evaluate the C artifact via FFI

No platform reimplements the Feistel by hand. One proved source, several
extraction targets — this is the whole defence against silent encode/decode
mismatch.

## Phase 7 — Later, unscheduled

- [ ] Coarse precision modes (two-word block, three-word room)
- [ ] Seed sharing between parties — needs ML-KEM
- [ ] Signed location attestations — needs SLH-DSA (hash-based, matches the rest
      of the design)
- [ ] Map tile rendering / visual grid overlay
- [ ] Revisit OxCaml if and only if profiling justifies it

## Open questions

- **Poles.** Cells near the poles are correct but geometrically poor: within
  the outermost bands, cell width falls well below 3 m. This is a design
  judgement no proof will make. Acceptable for now; revisit if polar use cases
  appear.
- **Round function source.** HACL\* verified HMAC-SHA256, or assume it at the
  interface? Bears on Phase 2 and Phase 6 sequencing.
- **Does `js/` survive the WASM port?** Settled for `reference/` — it goes at
  Phase 4. `js/` is the same category of liability but has a live argument for
  staying: an independently written implementation is a genuine check on the
  extracted one, in a way that a second extraction target is not. Decide at
  Phase 6. If it stays, it needs the same "scaffolding, do not cite as spec"
  framing as `reference/README.md`.
- **Does the server need to exist at all** for the core use case, or is it purely
  a convenience over a client-side library? Affects Phase 5 scope materially.
- **Altitude / floors.** Out of scope for now; note whether the address format
  should reserve room for it before the format is frozen.
- **Address space headroom.** Settled: 1.54× (65% fill). Confirmed against the
  generated table.
